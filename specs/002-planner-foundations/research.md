# Planner Foundations Research

Date: 2026-10-14; revised after architecture review. Source of product intent: [spec.md](spec.md), including R-01 to R-12 and Q-1 to Q-7. The decisions below supersede the original competing snapshot/transfer, marker-based validity and public two-phase design. This is source inspection and design, not implementation evidence. No database or development data was changed.

## Additional Planning Decisions Approved By The Product Owner

Two material gaps were surfaced rather than silently resolved to match existing code:

1. **Legacy starting boundary: option A.** Use an existing plan's first saved Gameweek squad as its explicitly assumed starting squad, retaining its initial bank/free-transfer value. The original squad was not persisted and cannot be reconstructed. This preserves legacy zero-first-Gameweek semantics at initialization; later edits use the new independent boundary. For a leading Free Hit, the inferred underlying squad is an assumption too, not recovered history. Do not substitute today's My Team or require a blocking historical reconstruction.
2. **Moving the start later: option B.** Rebase onto the evaluated permanent state immediately before the new start, including bank, ownership basis/provenance, available free transfers, Free Hit restoration and relevant chip usage in the removed prefix. This explicitly refines the spec's horizon edge case: declarations remain truthful after conversion into the rebased starting state, rather than blindly retaining old numerical inputs. The removed decisions are discarded as specified; no historical-version feature is added. The approved specification itself is not rewritten by this planning workflow.

## 2. Domain Ownership

**Decision:** Introduce a pure `fpl_engine.planning` aggregate evaluator and small rule extensions. Move the domain portions of API `plan_accounting.py` into it, leaving API adapters/mapping only. Inputs are typed immutable starting boundary, explicit GW transfer/chip/slot-lineup decisions, saved financial assumptions and rule metadata. Mutation validation compares replays of old and candidate canonical inputs. Output is evaluated squads, accounting, dependencies and diagnostics, never new transfer commands.

**Rationale:** The same calculation must serve creation, GET, edits, migration initialization and horizon rebase. A financial correction is not equivalent to a transfer edit. Rule ownership in FastAPI or React would make Q2/Q7 and FH behaviour diverge.

**Alternatives:** Independent service arithmetic or frontend rules are rejected. Reusing the Explorer transfer optimiser changes lineups and expands scope. A generic workflow/event-sourcing framework adds no value for at most 38 GWs and 15 players per squad.

Reuse `Chip`, `SeasonHalf`, `season_half`, `diff_squads`, `points_hit`, `has_unlimited_transfers`, corrected `free_transfers_after`, `SquadSlot`, `validate_squad`, `RuleViolationError` and existing projection/scoring code. Add integer-tenths selling-price arithmetic; declaration-aware chip validation/availability; deterministic propagation; permanent and temporary ownership transitions; dependency/provisional propagation; and resolution-aware candidate validation. Legal target pairs and captaincy transfer belong to engine rearrangement operations, not a second UI formation implementation.

## 3. State And Recalculation

**Decision:** The independent boundary plus explicit net-transfer/chip decisions and per-GW slot-role configurations are the single replay input. Full GW player membership is response output only. Stable slots carry incoming players into each GW's existing XI/bench/C/VC choices; explicit outgoing decisions bind player and ownership identity, not whichever player later occupies a slot. Each acquisition starts an ownership episode. No normal operation infers transfers from old materialized squads.

Capture market assumptions once for new/explicitly edited transfers. A replay must not consult live market prices for unchanged decisions, even during lineup saves, GET or ordinary FPL refresh. Integer tenths represent new money fields; display millions only at presentation boundaries. A whole-GW net replacement set supports same-deadline moves without requiring intermediate single-transfer affordability. Same-GW round trips remain unsupported.

Replay in GW order from the boundary: explicit valid net changes count in the first GW too; ordinary/WC results advance permanent state, FH restores it after temporary evaluation. FT is independent of the financial branch. Chip toggles change permanence/allowance, not the transfer set or quotes. Changing/removing an earlier acquisition can block a later outgoing decision; do not retarget it, invent another transfer or reprice it. Examples A/B in [data-model.md](data-model.md) define the result and explicit atomic repair. Fixed Q2 means a newly blocking upstream edit cannot commit alone; a repair batch preserves user control without a new invalid-edit exception.

**Derived-state decision:** Remove optional financial/status caches and new membership materializations. Retain only the saved selling-price output required by FR-035, reproducible from canonical basis/assumptions and updated atomically on correction. Old snapshot/accounting rows are quarantined migration data, never engine input after initialization. GET evaluates a coherent canonical revision without writes/repricing. Live projections/market values remain enrichment, not frozen underlying data.

**Alternative:** Persisting a separate full financial ownership snapshot for every GW creates additional mutable truths. An append-only transaction ledger or historical plan versions are unnecessary and out of scope.

## 4. Financial Provenance And Resolution

**Decision:** Starting provenance is `authoritative`, `user_confirmed` or `assumed`, with original source retained separately. Currently all unknown starting purchases use current market price as an estimate. A user-confirmed estimate never becomes authoritative historical evidence. Once initialized, prices are not refreshed automatically. Indicate estimates per player and once at plan level; provisional financial dependency is not the same as insolvency.

Persist outgoing market assumption, evaluated selling price and cost-basis source plus incoming acquisition price for each planned replacement. On provenance correction, recompute only dependent sales with saved market assumptions, retain incoming prices, and propagate bank/provisional changes. Editing an acquisition similarly changes downstream basis, but Q2 still governs acceptance of that explicit transfer edit. A later buy-back has a new independent basis.

Q7 accepts corrected starting provenance even if deficits appear. Derive every shortfall and financial dependency edge from replay, including earliest failure and descendants after a positive bank. FH temporary deficits stay plan issues without contaminating restoration. Remove persisted resolution markers: previous canonical inputs supply the comparison, not an issue ID or permission flag. Ordinary edits require candidate shortfall no greater than previous shortfall at every retained GW (new GW baseline zero), plus structural legality. Thus shortfalls `(1,3)` becoming `(0,2)` are an improvement, even though the earliest failure moves. Unrelated legal edits may retain unchanged old deficits. Correction source notes, if retained, are informational only.

**Alternative:** Rejecting a truthful correction, clamping negative bank, deleting decisions or treating provisional values as invalid contradicts Q6/Q7.

## 5. Automatic Persistence And Retry Identity

**Decision:** One public POST mutation operation, mutation ID/digest/expected revision and result lookup. No public prepare/commit endpoints. Retire legacy full-GW PUT/PATCH with 410 instead of maintaining writers lacking identity/preconditions. Creation/deletion remain normal resource operations. The coordinator queues captain/vice/swap/chip/transfer/purchase-price intents, resolves them against the latest acknowledged revision only at dispatch, and freezes the sent envelope for retry. It never queues complete lineup/squad payloads.

Retain a small server-private `validated_pending` receipt before the canonical-write transaction. This two-transaction internal sequence preserves accepted frozen financial inputs if the subsequent write rolls back; it is not a two-call browser protocol or a single atomic transaction spanning both stages. Acceptance starts only after the valid receipt is durable. Failure before that leaves a pending/unaccepted proposal. The canonical transaction atomically saves input changes, required selling-price outputs, revision and committed receipt. No caches/validity markers participate.

Committed IDs return `already_committed` plus committed revision/current plan, even after later revisions; never reapply. Pending IDs reuse captures only at a compatible unchanged base; otherwise `stale_reprepare_required`, with no old candidate reconstructed. Retain no historical base or complete candidate snapshot. A 404 lookup is not proof an original request finished: retry the same ID. The contract defines explicit 422/409/503 outcomes and accepted-unsaved retention. Rule-context compatibility excludes live market prices so ordinary refresh does not invalidate a quote retry.

**Rationale/alternatives:** A single atomic canonical transaction alone loses its quote receipt on rollback, so it cannot guarantee the same accepted quote on retry without another durability mechanism. Retaining a minimal private receipt is simpler than signed client quote tokens or historical candidate storage. The old public two-phase protocol, full-lineup commands, weaker compatibility writers and timestamp/debounce-only concurrency are rejected. Serial field-intent dispatch and committed-result lookup cover normal autosave in one request. Native unload is guarded, not guaranteed async persistence; cross-tab automatic merging remains out of scope.

## 6. Migration And Horizon Decisions

**Decision:** Add Alembic revisions after checked-in head `3e8b5d1a9c47`; verify head at implementation time. Keep old plan/GW/player rows and accounting columns untouched/quarantined; add canonical decision/slot/boundary/receipt storage. A controlled once-only engine-based application backfill runs before new editing is enabled, never in GET or by calling FPL. A rerun skips initialized plans. A deployment backup is operational protection, not a new per-plan rollback payload table.

Use owner-approved first-saved-GW membership, old bank/FT, no pre-used chips and assumed GW19 FH declaration. Convert later legacy net snapshot differences once against the inferred permanent state, restoring after FH, into explicit estimated decisions. Map saved lineups into stable slot roles. Freeze stored-market observations with `legacy_initialized_estimate`; fabricate no history. Old illegal inputs remain explicit diagnostics requiring repair; missing-price initialization fails atomically with a retryable report. Corrected financial output may differ from old cached arithmetic. There is no recurring snapshot-diff reconciliation.

Test upgrade/backfill/downgrade/re-upgrade only on isolated guarded fixtures. Before new edits, dropping additive schema leaves original legacy data unchanged, without restoration payloads. After new writes/plans, require explicit database backup/export and conversion/restore rather than claiming a lossless old-schema downgrade; refuse an unsafe in-place rollback. Never restore stale legacy snapshots over new edits or delete new plans to make downgrade pass. No development-data downgrade testing.

Moving start later captures the valid prefix's permanent exit as a new boundary, preserving slot/ownership identity, inline basis/source values, bank assumptions and FT before trimming. No dangling reference to a deleted acquisition decision. Carry only declarations/chips relevant to the new period and FH19 at new GW20. Reject blocked/unresolved prefixes. Earlier starts add empty decisions against a hypothetical boundary, not invented history; compatible declarations must accompany the mutation. Extensions add empty decisions after permanent FH restoration. No horizon edit infers new transfers from old output squads.

## 7. Verification And Remaining Risk

Existing tests: `packages/fpl_engine/tests/test_rules.py`; API `tests/plans/test_plan_accounting.py`, `test_plan_services.py`, `test_get_plan_view_service.py`, `test_plans_router.py`; web `tests/plans/plan-board.test.tsx` and `tests/team/my-team-board.test.tsx`. Existing router tests use fakes; no current Planner repository/migration suite proves transaction guarantees. Some fixtures are unrealistic and old WC/FH expectations must intentionally change.

Use focused engine tests for all rules/ownership branches; service tests for command orchestration/pricing capture; guarded PostgreSQL tests for atomicity, uniqueness, retry/revision races and reversible migration; component tests with deferred promises/stateful fixtures for sequencing and error retention; durable realistic Planner Playwright journeys and final desktop/mobile browser inspection. Artificial correction/FH/deficit cases use deterministic synthetic data, not development mutations. Detailed scenarios and commands are in [quickstart.md](quickstart.md).

No product question remains blocking this design after the two additional answers above. Main risks are irrecoverable legacy baseline information, changing snapshot-based propagation into ownership-aware replay, transaction/response-loss semantics, live player metadata that can make old squads illegal, and reversible legacy initialization. Rule changes must not accidentally broaden My Team/Explorer pricing or change projected-points logic. Runtime, migrations, integration and browser results are not claimed by this research.
